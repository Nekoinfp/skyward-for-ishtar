# Skyward v1.1.0 for Xiaomi 15 Ultra (xuanyuan)

```
底包：HyperOS OS4.0.4.0.XOACNXM 原厂 recovery，AVB footer 算法 NONE。
      recovery 分区 SHA-256 55f491052a360bc15362fd80c8bd2dd0912b289e1653f2bd7f9c5a12e7fea27b
      （已与底包 payload.bin 清单里该分区的声明哈希核对一致）
适用：小米 15 Ultra（xuanyuan），已解锁 Bootloader。
```

> **这一版没有做真机验证。** 下面的“已验证”指在电脑上跑通的测试与编译，
> 不包含任何一台实机上的解密、刷写或扩容。刷之前请先备份，见文末。

## 相对 v1.0.0 的改动

### 解密

- **底包从 OS4.0.0.18 升到 OS4.0.4.0**。v1.0.0 是在 4.0.0.18 上打包的，而手机跑的是
  4.0.4.0。recovery 的 AVB footer 会把底包的安全补丁级别交给引导程序、再传给安全世界；
  与已装系统对不上时，KeyMint 会拒绝系统做出的密钥。用同版本底包打包，至少把这个变量去掉了。
  （4.0.4 上解不开 data 的确切原因没有逐条验证过：上游 issue #64 记录的直接原因是
  `keymint` 缺 `libvndksupport.so`，那条链路由适配分支的补库逻辑修复；
  footer 补丁不一致只是另一个已知会挡住密钥的原因。真机失败时看
  `skyward check` 与 `/skyward/run/services/` 下的日志，两者能区分开。）
- **服务自己的错误输出不再丢弃**：以前每个服务都以 `stderr` 丢进 `/dev/null`，
  `CANNOT LINK EXECUTABLE … library "libvndksupport.so" not found` 这种唯一能定位问题的
  一行被直接扔掉。现在写到 `/skyward/run/services/<程序名>.log`，超过 64 KiB 清空重写。
- **weaver 调用 4 秒超时**：安全元件不应答时，界面不再被驱动的默认等待拖住几十秒。
- **`adb shell skyward check`**：一条命令打印槽位、底包、已装系统、手机自己表里
  `/data` 的加密参数、密钥目录内容（只列名字和大小）、密钥链各服务是否注册、
  更新状态，以及每个服务错误输出的最后几行。要更全的一份，用
  `tools/collect-report.sh`，它把这台电脑能取到的都收进一个文件。
- **`skyward` 这个名字现在真的存在于 ramdisk 里**（`/system/bin/skyward`，指向同一个
  二进制）。以前只有 `/system/bin/recovery`，而它按启动时的名字决定当服务还是当命令，
  所以 `info`、`update`、`lp`、`data`、`check` 这些子命令在手机上根本调不到。

### 刷写

- **逻辑分区可以扩容**：镜像比现有分区大时，用 super 的**空闲空间**新增 extent，
  不移动、不改写任何既有 extent，也不碰另一槽位的分区；两槽一起规划、整体校验后才提交
  元数据。元数据的主备两份都写并回读校验。
- **sparse super 并行写入**：4 个 4 MiB 缓冲，一个读线程预读、主线程写。
  写盘前完整校验格式；`DON'T CARE` 区间**原样保留**（不清零、不 discard），
  因为那是 super 里其它分区的地方；CRC32 记录逐段校验，不符即失败。
- **脚本类 zip 查设备**：这类包自带 updater 直接写分区，以前完全不看 `pre-device`。
  现在写了 `pre-device` 且不含本机的包会在确认之前被拒绝。
- **单分区镜像与文件系统镜像分开处理**：是分区镜像才搬 AVB footer、才可以先 discard；
  逻辑分区的文件系统镜像两者都不做。

## 未实现（与 v1.0.0 相同）

- **snapuserd 压缩快照的更新、增量更新包**：原厂 recovery 版 `update_engine_sideload`
  在 recovery 里直接关闭 VABC，增量 payload 会在 `DeleteSourcePartitions()` 报错。
  这不是“打开一个开关”能解决的，需要与固件匹配的 `libsnapshot`/`snapuserd`。
  目前保持**显式拒绝**，不会半途写坏。
- **非 A/B 机型的更新包**：xuanyuan 是 A/B 机型，让别人的非 A/B 包在本机跑通没有意义。

## 构建产物

完整的核对清单与真机验证步骤见 `docs/xuanyuan-verification.md`。

本分支在 Linux 上（WSL 里的 Ubuntu 24.04 + NDK r29）实际构建过一份：

```
104,857,600 字节
SHA-256 31ff629ef854529d6c712328b0aa030e1b2b561cd3d55fbb76b2dde157ca3dcc
```

底包 recovery 分区由打包器自己从 4.0.4.0 更新包里取出，并核对 SHA-256
与 `devices/xuanyuan.toml` 一致（`55f49105…7fea27b`），对不上会直接失败。

镜像内容逐项核对过：

| 项 | 结果 |
| --- | --- |
| 形状与底包一致 | `ANDROID!`、header_version 4、kernel 0、104,857,600 字节 |
| `system/bin/recovery` | Skyward 本体，8994824 字节 |
| `system/bin/skyward` | 存在（链接），子命令可调用 |
| 脚本命令链接 | 7za / avbctl / resetprop / unzip / zstd 全在 |
| `skyward/device.toml` | 与仓库里的 `devices/xuanyuan.toml` **逐字节相同** |
| `skyward/system-init`、`skyward/permissive-init` | 都在 |
| OMAPI | `system/bin/se_omapi` 与 `system/etc/vintf/manifest/se_omapi.xml` 都在 |
| `prop.default` | 已移除构建版本属性，末尾为 `ro.secure=0`、`ro.adb.secure=0`、`ro.debuggable=1`、`ro.ota.allow_downgrade=true` |

**它仍然没有在任何手机上运行过。**

关于打包时那条 `names no security patch in its footer` 警告：4.0.4.0 底包 recovery 的
AVB footer 里只有一个 `com.android.build.recovery.fingerprint`，没有 `security_patch`
也没有 `os_version`；而出货的 v1.0.0 镜像 footer 里**一个属性都没有**。所以这不是 4.0.4
独有的退化，打包器只是保守地提示。recovery 自己在启动时会把已安装系统的版本与补丁级别
写进属性并重启密钥服务（`adopt_installed_version` + `environment::pin`）。

## 已验证

在本分支的干净工作树上，用 Linux（Ubuntu 24.04，rustc 1.100.0）：

```
cargo test --workspace                    # 全部通过，0 失败
cargo clippy --workspace --all-targets -- -D warnings   # 退出码 0
```

其中 `skyward-install` 159 项、`skyward-lp` 22 项、`skyward-config` 29 项都包含在内
（sparse 的 9 项就在 `skyward-install` 里）。里面有两组确定性随机测试：12 轮随机
sparse 镜像与独立实现逐字节比对，40 轮随机扩容与它承诺的条件逐条比对。

顺带在这一轮跑出了这份 fork **原本就存在**的三个失败（它的 CI 一直是红的）并修好了：
`copy()` 在读取出错时丢掉缓冲区里已读到的字节，导致 `zstd -d` 与 `unzip -p` 少写最后一段，
`unzip -t` 也因此从不报告坏 CRC；`spans()` 把正好三个窗口长的镜像当成"太短"。

## 注意事项

- super 与超过 512 MiB 的镜像写完只 sync、只比对窗口，不整盘回读；**刷完请立即重启**。
- **扩容前请备份 super**：`dd if=/dev/block/by-name/super of=/sdcard/super_stock.img`。
  提交元数据不是掉电原子操作，中途断电需要重刷完整 super 才能恢复。
- 曾用测试版禁用过 AVB、开机卡 fastboot 的：进本 recovery 再执行一次禁用 AVB2.0 即可，
  或在 fastboot 刷回原版 vbmeta：
  ```bash
  fastboot --disable-verity flash vbmeta_a vbmeta.img   # _b 同
  fastboot flash vbmeta_system_a vbmeta_system.img      # _b 同
  ```

## 刷入

先备份原厂 recovery，再刷入两个槽位：

```bash
dd if=/dev/block/by-name/recovery_a of=/sdcard/recovery_a_stock.img
dd if=/dev/block/by-name/recovery_b of=/sdcard/recovery_b_stock.img

fastboot flash recovery_a skyward-v1.1.0-xuanyuan-OS4.0.4.0.XOACNXM.img
fastboot flash recovery_b skyward-v1.1.0-xuanyuan-OS4.0.4.0.XOACNXM.img
fastboot reboot recovery
```

进 recovery 后先跑 `adb shell skyward check`，把输出留下来；解密、刷写、扩容中任何一步
不对，这份输出就是排查的起点。详见 `docs/xuanyuan-os404.md`。
